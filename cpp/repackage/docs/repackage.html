mcap-repackage: rationale, algorithm and performance

Re-chunking MCAP files for smaller size and faster reads. Built on the multithreaded mcap::ParallelReader.

1. Why repackage?

An MCAP file is a sequence of records grouped into chunks. Each chunk is independently compressed (zstd or lz4) and is indexed by a chunk index (start time, end time, byte offset) plus, optionally, a per-channel message index for random access inside the chunk. The layout chosen by the writer — how messages are grouped into chunks, and in what order within each chunk — is a one-time decision that the reader cannot undo without rewriting the file.

Most MCAP writers (including rosbag2, the canonical ROS 2 recorder) chunk messages in arrival order. Inside a single chunk you therefore find an interleaved soup of all topics that were active during that time slice. That is the natural thing to do while recording, but it has two costs that a downstream consumer pays forever:

  1. Compression ratio. zstd compresses by finding repetition within a sliding window (typically tens of KiB to a few MiB). When messages from one topic — same field layout, same repeated frame_ids, same enum constants — are interleaved with unrelated messages from 100+ other topics, the repetition is dispersed and the window keeps churning. Co-locating same-topic messages packs that repetition into a small region zstd can exploit fully.
  2. Chunk geometry. Recorders tend to emit small chunks to keep memory bounded and to flush often. The result is hundreds of small chunks per file, each with its own index. Random-access reads pay per-chunk overhead (index lookup, decompressor setup, partial decode), and the parallel reader has fewer independent units to pipeline across cores.

mcap-repackage rewrites the chunk layout to remove both costs without altering message content, message order in log-time, or any metadata. The output is a fully valid, fully indexed MCAP file that any conforming reader will accept.

2. What the tool produces

A repackaged file has the same messages, channels, schemas, attachments, metadata, profile, and library string as the input, but its chunks are different in three concrete ways:

  1. Time-disjoint chunks. Messages are read in log-time order and packed into a buffer until the buffer reaches the target --chunk-size (default 4 MiB uncompressed). Each chunk therefore spans a contiguous slice of log time and chunks do not overlap. A log-time read needs no cross-chunk merge: it can stream chunks in file order.
  2. Topic-adjacent within a chunk. Before writing, the buffer is stable-sorted by (channel_id, log_time, sequence). zstd sees long runs of same-topic payload and compresses far more aggressively.
  3. Large messages isolated. Any message at or above --large-message-threshold (default 256 KiB) is written as its own single-message chunk. This prevents one outsize payload — a point cloud, an image — from forcing a selective reader to decompress hundreds of unrelated small messages that share its chunk, and prevents it from poisoning the zstd window for the small messages.
Important property — lossless w.r.t. message order. Because chunks are time-disjoint and messages within a chunk carry their original log-time, a log-time read of the repackaged file returns exactly the same sequence as a log-time read of the input. The within-chunk sort by channel is a layout optimisation, not a re-ordering of the playback stream.

3. Algorithm (architectural view)

3.1 Pipeline

┌──────────────────────────────────────────────────────────────┐ │ INPUT MCAP (mmap'd) │ └──────────────────────────────────────────────────────────────┘ │ read summary (chunk + message indexes) ▼ ┌──────────────────────────────────────────────────────────────┐ │ ParallelReader: thread pool decompresses ahead │ │ (k-way merge across chunks in log-time order) │ └──────────────────────────────────────────────────────────────┘ │ one message at a time, in log-time order ▼ ┌──────────────────────────────────────────────────────────────┐ │ Repackager (single thread) │ │ • re-register schema/channel on writer (first seen) │ │ • if size ≥ large-threshold → flush, emit alone, flush │ │ • else append to buffer; if buffer ≥ chunk-size → flush │ │ flush: stable_sort(buffer, by channel, log_time, sequence) │ │ for each msg: writer.write(msg) │ │ writer.closeLastChunk() │ └──────────────────────────────────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ McapWriter (zstd / lz4 / none) │ │ emits time-disjoint chunks + message indexes + summary │ └──────────────────────────────────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ Copy metadata + attachments (original file order) │ │ Write summary section + footer │ └──────────────────────────────────────────────────────────────┘ │ ▼ OUTPUT MCAP

3.2 The three data-flow rules

Every decision in the Repackager comes from three rules. They are deliberately simple, because the time-disjoint property follows automatically when messages arrive in log-time order:

RuleTriggerAction
R1 — isolate large msg.dataSize ≥ largeMessageThreshold Flush current buffer, emit the large message alone, close its chunk.
R2 — size-bounded flush buffer_payload + msg.dataSize > chunkSize (and buffer is non-empty) Flush current buffer, then append the message to a fresh buffer.
R3 — ordinary append otherwise Append message to the buffer.

“Flush” means: stable-sort the buffered messages by (channel_id, log_time, sequence), write them sequentially through the McapWriter, then call closeLastChunk(). The sort is stable so messages that share a channel keep their log-time order, and ties on log-time fall back to the original sequence number. Because every message in the buffer was appended in log-time order, the buffer holds a contiguous time window before sorting; sorting by channel re-orders inside that window but the window’s [start, end] times are unchanged. The next chunk’s window starts at or after the previous chunk’s end — chunks are time-disjoint by construction.

3.3 Read path: parallel when possible, serial fallback

The read side picks between two paths based on what indexes the input has:

  • ParallelReader when every chunk has a message index (or at least one does). Workers in a fixed-size thread pool prefetch and decompress chunks ahead of the consumer; a bounded byte-semaphore caps how many decompressed chunks are resident at once (memoryCap mode ChunkCount is used for the repackager, which is neutral-to-faster for a full sequential read).
  • Serial fallback for unchunked files, or chunked files with no message indexes. The serial path assumes the input is approximately log-time ordered (which is how every common recorder writes).

3.4 Why time-disjointness is the load-bearing property

Most chunk-layout proposals in MCAP-adjacent tools either (a) sort the whole file by topic, or (b) interleave chunks freely and trust the reader to k-way merge them. The time-disjoint, topic-adjacent-within-chunk layout is a deliberate middle ground:

  • A reader that wants all messages in log-time order streams chunks in file order with no merge — one decompressor, one cursor.
  • A reader that wants only some topics uses the per-chunk message indexes; it still touches every chunk that overlaps the time range, but each chunk yields its topic-of-interest messages contiguously after decompression (better cache behaviour and a smaller decompressed payload because the chunk itself is smaller).
  • A reader that wants a time window skips every chunk whose [start, end] is outside the window. With time-disjoint chunks there is no false positive, so the smallest possible set of chunks is decompressed.

4. Benchmark: dexory dataset

Two representative recordings from the ~/ws_plotjuggler/DATA/dexory set (197_continuous_*.mcap, 200_continuous_*.mcap): ROS 2 bags, 20 min each, ~84 MB compressed on disk, ~357 MiB uncompressed payload, 1.28 M messages across 162 topics, 481 chunks each. /tf is the per-experiment small target: ~90,000 messages at 75 Hz, ~33 MiB of payload (~10 % of total), one of ~160 active topics.

Hardware: local NVMe SSD; warm-cache runs follow a cat file > /dev/null; cold-cache runs evict the file via posix_fadvise(POSIX_FADV_DONTNEED).

On cold cache the smaller file matters more: the repackaged file moves 42 % less byte traffic from disk, and the parallel-4 reader pipelines that I/O against decompression effectively enough that the selective /tf read becomes 35 % faster wall-clock. On a network filesystem or a slower disk the I/O gap would dominate the comparison further.

4.4 What this implies for production workloads

  • Storage cost. 42 % smaller files on a representative ROS 2 bag with 160+ topics. For a dataset measured in TB this is the first-order win.
  • Selective topic reads (the common case for analysis tools like PlotJuggler) get faster proportionally to how much they were I/O-bound: marginal on warm SSD, significant on cold or remote storage.
  • Full-bag replays (e.g. simulation) are decompression-bound and see modest or no speedup — but they also do not regress.

When not to use it. The repackager is a batch tool. It loads chunks ahead, decompresses everything, and writes a new file — it is not appropriate for live recording, and it should not be run in the inner loop of an analysis pipeline. The expected use is “archive once after a recording session, read many times afterward.”

6. Replicating the algorithm

A second implementation in any language with an MCAP reader/writer needs the following pieces. None of them require touching the MCAP format itself; this is purely a re-layout of records.

6.1 Required reader capabilities

  1. Log-time-ordered iteration over all messages, with per-message access to (channel_id, schema_id, log_time, publish_time, sequence, data, dataSize) and to the source channel + schema records.
  2. Summary access: list of chunk indexes, message indexes, metadata indexes, attachment indexes (to know what to copy through verbatim).
  3. Random-access record reads at a byte offset (to copy attachment/metadata bodies through without re-parsing).
  4. Optional but recommended: a concurrent (mmap-backed) source so multiple decompressor threads can read disjoint byte ranges in parallel. This is what the C++ ParallelReader requires of its source.

6.2 Required writer capabilities

  1. Explicit chunk boundary control. The implementation MUST be able to force a chunk close at a chosen message (called closeLastChunk() in libmcap C++). Without this you cannot implement size-bounded flushes or large-message isolation.
  2. Per-message append into the current open chunk (write(Message)), with the writer maintaining its own message index for that chunk.
  3. Schema and channel registration with writer-assigned IDs. The repackager keeps two maps: input schema id → output schema id and input channel id → output channel id, populated the first time each input ID is seen.
  4. Compression configuration (zstd / lz4 / none, level, CRC on/off).
  5. Verbatim attachment + metadata write. The implementation must accept the raw bytes of an attachment and the raw key/value pairs of a metadata record, so the output is byte-identical with the input for those records.

6.3 Algorithm skeleton

open(input_path)             # mmap if the reader supports concurrent reads
read_summary(input)
configure writer:
    profile = input.header.profile
    library = input.header.library
    chunk_size_target = chunkSize     # user option, default 4 MiB
    compression       = zstd|lz4|none # user option, default zstd
    compression_level = ...           # default = compressor default
    chunk_buffer_reserve = max(256 MiB, chunkSize, largeMessageThreshold)
                                      # clamped to a safe ceiling (2 GiB)
open output stream(output_path)

schema_map  := {}   # input_schema_id  -> output_schema_id
channel_map := {}   # input_channel_id -> output_channel_id

buffer       := []  # messages pending in the current chunk
buffer_bytes := 0

for msg in reader.read_messages(LogTimeOrder, on_problem):
    cid_out := ensure_channel(writer, msg.channel, msg.schema, schema_map, channel_map)

    if msg.dataSize >= largeMessageThreshold:
        flush(buffer)                       # close current chunk (sort+write+close)
        writer.close_last_chunk()           # idempotent if empty
        writer.write(Message{cid_out, ...,  # emit isolated
                             data, dataSize})
        writer.close_last_chunk()           # large-message chunk closes immediately
        continue

    if buffer_bytes > 0 and buffer_bytes + msg.dataSize > chunk_size_target:
        flush(buffer)

    buffer.append((cid_out, msg.sequence, msg.logTime, msg.publishTime, copy(msg.data)))
    buffer_bytes += msg.dataSize

flush(buffer)                               # final chunk

copy_metadata_and_attachments(reader, writer)   # in original file order
writer.close()

where flush is:

function flush(buffer):
    if buffer empty: return
    stable_sort(buffer, key = (channel_id, log_time, sequence))
    for m in buffer:
        writer.write(Message{...})
    buffer.clear()
    buffer_bytes := 0
    writer.close_last_chunk()

6.4 Channel/schema re-registration

A channel is registered exactly once per output writer; reusing it for subsequent messages keeps the channel-id space small and matches what the input had. If the input channel references a schema id that the input never declared (corrupt input), fail fast and abort — do not silently write a schema-less channel. 

function ensure_channel(writer, ch_in, sch_in, schema_map, channel_map):
    if ch_in.id in channel_map: return channel_map[ch_in.id]

    sch_out_id := 0
    if ch_in.schema_id != 0:
        if sch_in is null:
            abort("channel references missing schema")
        if ch_in.schema_id not in schema_map:
            sch_out := Schema(sch_in.name, sch_in.encoding, sch_in.data)
            writer.add_schema(sch_out)             # writer assigns sch_out.id
            schema_map[ch_in.schema_id] := sch_out.id
        sch_out_id := schema_map[ch_in.schema_id]

    ch_out := Channel(ch_in.topic, ch_in.encoding, sch_out_id, ch_in.metadata)
    writer.add_channel(ch_out)                     # writer assigns ch_out.id
    channel_map[ch_in.id] := ch_out.id
    return ch_out.id

6.5 Metadata and attachments

Walk the reader’s metadata-index and attachment-index lists, sort by file offset (so the output preserves their original order), read each record raw, parse just enough to extract the fields the writer needs (name, key/value pairs, or raw bytes), and call the writer’s metadata / attachment write methods. If the summary indexes are missing or visibly incomplete (count mismatch against statistics), fall back to a forced scan of the file to rebuild them — otherwise an output would silently lose records.

6.6 Optional: parallel decompression

The repackaging algorithm itself is single-threaded by construction (one ordered consumer). The read side, however, parallelises trivially because every chunk is independently decompressible. A useful pattern (used by the C++ ParallelReader):

  • A fixed-size worker pool decompresses chunks ahead of the consumer.
  • A bounded byte-budget (back-pressure semaphore) caps resident decompressed bytes so a fast pool does not exhaust memory ahead of a slow consumer.
  • A k-way merge heap over the chunks’ per-channel message indexes yields messages in log-time order. Each chunk is decompressed at most once; cursors keep a shared pointer pinning their chunk so it survives until the cursor drains.

This pattern accelerates the read step by ~2× with 4 threads on a typical workstation; for the dexory full read, repackaged file: 0.31 s serial → 0.16 s parallel-4 (warm cache). It does not change the output of the repackager; correctness is identical to the serial path.

7. Caveats and library quirks

  • Chunk-size ceiling. The libmcap C++ writer’s chunk buffer is reserved to its configured chunkSize, so the repackager picks a ceiling that is at least as large as the target chunk size and the large-message threshold, clamped to 2 GiB. A --chunk-size above that cap, or pathologically tiny messages, may add a benign extra chunk boundary at the ceiling — never data loss. The default 4 MiB is well within the cap.
  • Compression-level mapping. The C++ writer exposes only five levels via CompressionLevel: Fastest=1, Fast=3, Default=1, Slow=5, Slowest=7. Level 0 is treated as Default (zstd 1). zstd 1 is the recommended default: with parallel decompression the read-time cost of a higher level is hidden, while the on-disk size gain plateaus quickly.
  • Unindexed inputs. A chunked input that has chunk indexes but no message indexes cannot be read in log-time order by libmcap C++ — the tool falls back to file order, which assumes the input is approximately log-time ordered (true for every common recorder). The Rust reader, by contrast, re-derives order by decoding chunks; a port using the Rust reader would not need this caveat.
  • Error policy. Any read problem surfaced via the reader’s problem callback (truncated record, decompression failure, missing channel) is fatal: the writer is terminated and no output is produced. This matches what rust/cli mcap convert does and is the only safe behaviour when the output is meant to replace the input.
